## 2. 首页职责图（对照 `docs/home-community-direction.md`）

| 栏目 | 本次设计中的唯一职责 | 明确不做的事 |

| 附近（不在本次范围，仅标注边界） | 保留完整活跃心愿市场：列表/搜索/筛选/详情/响应 | 不承载已完成故事归档 |

## 3. 页面与状态覆盖

### 3.1 `10_Home_Normal.html` 首页正常态

- 顶栏：品牌字标 + 通知铃铛（视觉 34pt，需要 `.contentShape` 补足 44pt 命中区，与 CL-003 顶栏铃铛同一处理方式）。
- 去框化 Hero：标题 23pt/700，副标题 13pt/ink-500，其下并排一个实心主按钮"我也想发布心愿" + 一个文字次按钮"去附近看看能帮什么 ›"（`accent` 色文字，无边框）。这是 `docs/reviews/v31-candidate-review.md` 已采纳为候选的"更简洁 Hero"方向，本次在 CL-005 范围内首次落地为正式交付。
- 故事流（竖向 `ScrollView`）：
  - **第一张卡**：完整状态，含媒体占位（16:7 比例，`canvas-sunk` 底色 + 居中图片类 SF Symbol 图标）、视频类型右下角播放徽标、类型 Chip、脱敏地点+相对时间、心愿正文（2 行截断）、"如何完成"一句话、引用式感谢语（`canvas-sunk` 底色块）、右下角点赞图标（仅描边，无数字，见第 7 节）。
  - **第二张卡**：`text-only` 变体，媒体占位区域整体不渲染，改为一行"发布者未上传交付图片"提示 + 图标，其余结构不变——用于验证"缺失媒体"仍是一条完整、不破损的故事，不是渲染错误。
  - **第三张卡**：故意只露出媒体区域顶部（140pt，非完整卡片高度），被浮动 Dock 的半透明材质部分遮盖，向下延伸到屏幕底部之外，呼应"内容在浮动 Dock 下连续滚动"的系统行为。裁切边界落在纯色媒体块上，不落在文字行中间；这与 `CL-003` 首页横向卡"第三张卡 49pt peek"的既有设计语言一致，是同一手法在竖向流中的延伸，不是新发明的裁切规则。
- 浮动 Dock：见第 5 节单独说明。

### 3.2 `10_Home_Empty.html` 首页空态

- 复用相同顶栏与 Dock，保证空态与正常态的产品 chrome 一致。
- 诚实空态：图标（堆叠/卡片语义）+ 标题"还没有可公开的完成故事" + 说明文案，明确解释原因是"需要发布者单独同意"而不是加载失败或系统故障，不使用任何伪造推荐或占位假故事。
- 因为没有内容可浏览，两个转化出口从 Hero 里的次要动作升级为空态区域的主要动作：主按钮"我也想发布心愿"、次按钮"去附近看看能帮什么"，均为整行按钮，比正常态 Hero 里的行内按钮更醒目。
- 底部隐私提示条：强调"不显示联系方式与精确地点，随时可申请下架"，让用户即使在空态也能理解内容安全边界。

### 3.3 `11_Story_Detail.html` 故事详情 · 沉浸阅读态

- 媒体延伸到状态栏下方（404pt 高度），状态栏时间与返回/点赞按钮均为浮层圆形按钮（34pt 视觉，需 `.contentShape` 补足命中区），不额外绘制导航栏背景，让阅读从图片开始。
- 内容面板以 `r-lg` 顶部圆角"浮起"覆盖媒体下缘（覆盖约 30pt），带一个 `hairline-strong` 小抓手条，视觉上呼应可下拉的 Sheet/详情语义（实现上是普通 `ScrollView` 内容区，不是真正的 Sheet，抓手条只是阅读区起点的视觉锚点，不需要手势响应）。
- 内容顺序严格遵循蓝图的"心愿正文 → 如何完成 → 交付片段/感谢"：类型 Chip + 脱敏地点/时间 → 心愿完整正文（不截断）→"如何完成"小节标题 + 叙述段落（不透露响应者身份，只说"一位附近、通过人工审核的朋友"）→ 引用感谢语块（署名"— 心愿发布者"，不用真实姓名）→ 分隔线 → 两个转化出口（整行按钮，主/次分明）。
- **本页不显示浮动 Dock**：这是 `NavigationStack` 内的 push 详情页，建议实现使用系统 API `.toolbar(.hidden, for: .tabBar)` 在推入详情时隐藏 Tab Bar，属于系统支持的原生用法，不是手工遮挡或重写 Tab 行为；沉浸阅读区因此不被导航元素打断。若产品负责人希望在详情页保留可见 Dock，也可改为不隐藏，两种都是系统原生行为，不影响本设计的其余部分。

### 3.4 未在本检查点渲染像素、但已在此文档说明的状态

任务卡要求列出"缺失媒体/无授权内容/加载/错误状态与转化路径"，其中缺失媒体与无授权内容（空态）已经在上述两个页面中真实渲染；加载与错误未各画一张独立像素稿，原因和 CL-003 附近页的加载/空/失败三态处理方式一致——检查点只保证结构和 token 到位，具体如下，供实现者和下一检查点直接使用：

- **首次加载**：故事流位置用骨架屏，建议用 3 个 `canvas` 卡片轮廓 + `canvas-sunk` 内部占位块，禁止用系统菊花独占全屏（会造成白屏观感）；Hero 与顶栏保持不变，不整体替换为骨架，参考 `docs/ios-experience-blueprint.md` 的"内容位骨架或简洁进度；保留导航，禁止白屏"。
- **加载失败/网络错误**：在故事流位置显示与 `10_Home_Empty` 相同结构的提示模块，但图标换成 `exclamationmark.triangle` 语义、标题改为"暂时无法加载故事"、按钮改为单个"重试"，不与"我也想发布/去附近"两个转化出口混在一起（失败态的首要动作是重试，不是引导离开）。
- **单条故事媒体加载失败**（图片/视频拉取失败，但列表本身成功）：媒体占位区保留、图标换成"失败"语义（例如 `exclamationmark.triangle`），不隐藏整条故事，因为文字内容仍然完整可读。

## 4. 故事卡最小字段

| 字段 | 说明 | 是否必需 |
| --- | --- | --- |
| 心愿正文 | 发布者原始心愿表述，卡片截断 2 行，详情页完整展示 | 必需 |
| 如何完成 | 一句话概括交付方式，不透露响应者姓名/联系方式 | 必需 |
| 感谢语 | 发布者反馈引用，署名统一用"心愿发布者"，不用真实称呼 | 建议，缺失时故事仍可发布（结构需能容忍空值） |
| 脱敏地点 | 仅到城市级别，不含精确地址/地标门牌 | 必需 |
| 完成时间 | 相对时间（"N 天/周前完成"），不展示精确日期时间戳 | 必需 |
| 交付方式标签 | 复用 `docs/ios-api-contract.md` 的 `DeliveryType` 语义（现场录像/手写卡片/到场陪伴等） | 必需 |
| 媒体 | 图片或视频缩略图，可为空（见 3.1 第二张卡的 `text-only` 变体） | 可选 |
| 点赞状态位 | 仅视觉预留，见第 7 节 | 可选、非本轮功能 |

不存在的字段：响应者称呼/头像、联系方式、精确坐标、能力 URL/token、账号关系（好友/关注）——这些字段不应出现在故事卡的数据模型里，而不只是"UI 上不显示"，因为 `docs/home-community-direction.md` 要求内容源头就不允许这些信息进入公开流。

## 5. 浮动 Liquid Glass Dock 的设计意图与实现边界

三个页面里，`10_Home_Normal`/`10_Home_Empty` 底部都画了一个浮动胶囊：四周 18pt 留白、64pt 高、`999px` 全圆角、半透明白底 + `backdrop-filter: blur(20px) saturate(180%)`。这是**给 Codex/实现者的视觉沟通稿**，不是要求手工实现这份 CSS：

1. 真实实现必须使用 SwiftUI 原生 `TabView`/系统 Tab Bar，让 iOS 26+ 系统自己渲染浮动 Liquid Glass 材质、处理透明度、对比度、"降低透明度"辅助功能选项和版本回退（iOS 16–25 自动退回系统默认 Tab Bar 外观）；不得照抄本稿的 `backdrop-filter`/`border`/`border-radius` 数值去手写一个自定义 Dock 组件。
2. 本稿刻意**没有加 `box-shadow`**：`docs/ios-design-freeze-v3.md` 明确"iOS 26 系统 Liquid Glass 的平台材质/高光不属于自定义阴影例外"，所以浮动 Dock 的立体感完全靠系统材质本身，本设计稿不通过阴影模拟浮起效果，避免被误读成"这里需要一个新的阴影例外"。
3. 五个目的地（首页/附近/发布/进度/我的）必须保留系统可访问名称、44pt 最小点击区和 VoiceOver 语义；非选中状态是否常驻显示文字标签由系统平台样式决定，本稿为了设计沟通清晰，所有状态都画了文字标签，不代表要求强制常驻文字。
4. 首页内容在 Dock 下方"连续滚动"的效果，本稿用第三张故事卡被 Dock 局部遮盖来示意（见 3.1）；真实实现中这是 `ScrollView` 内容延伸到安全区之下的自然结果，不需要额外处理。

## 6. Token / SwiftUI 映射

沿用 `docs/ios-design-freeze-v3.md` 已冻结的 token，本次没有新增颜色/圆角/间距级别：

- 背景：页面 `canvas-warm #FBF6EC`；卡片/按钮/浮层 `canvas #FFFFFF`；媒体占位/引用块/输入态 `canvas-sunk #F3ECDD`。
- 文字：主文字 `ink-900 #171310`（标题、正文、主按钮文字）；次文字 `ink-700 #4A443C`（如何完成、引用语正文）；三级文字 `ink-500 #847C6F`（元信息、说明文案、次按钮边框色系）；四级 `ink-300 #C4BBAC`（占位图标、未激活 Tab）。
- 描边：`hairline #E9E1D2` 卡片/按钮描边、分隔线；`hairline-strong #D8CDB8` Chip 描边、抓手条。
- 强调色：`accent #3E6B92` 仅用于详情页的次要文字链接"去附近看看能帮什么"（Hero 里的次按钮同色）。
- 圆角：`r-md 14pt` 按钮；`r-lg 20pt` 卡片、媒体占位区顶角、详情页内容面板顶角；`r-pill 999pt` 头像式圆形按钮（铃铛/返回/点赞）与浮动 Dock、Chip。
- 间距：8pt 网格，卡片内边距 16pt，卡片间距 16pt，Hero 与故事流之间留白通过 `feed-label` 的上下 margin 控制，未引入新的间距级别。
- 字体：标题对应 `.title2`/自定义 23pt（Hero 主标题，视觉上接近 `.title2` 加粗，SwiftUI 落地建议直接使用 `.title2.weight(.bold)` 而非写死 23pt，保持 Dynamic Type）；卡片心愿正文对应 `.headline`；元信息/说明对应 `.footnote`/`.caption2`。所有字号在 HTML 中是像素字面量，SwiftUI 实现必须换成语义字体，不得按字面像素值写死。
- 图标：全部为内联 SVG 手绘，风格对齐 SF Symbols Regular、约 1.6–1.9pt 描边，落地时应直接替换为对应 SF Symbols（如 `bell`、`heart`、`photo`、`play.fill`、`chevron.left`、`square.stack`），不需要真的用这份 SVG 作为最终资源。

## 7. 点赞：设计注记，不是功能交付

三个页面里的心形图标（故事卡右下角、详情页右上角浮层）**只是视觉预留**，均为纯描边、无填充选中态、旁边不放数字。这不是本轮要实现的功能，上线前必须先具备：

1. 账户体系（当前 MVP 无登录，点赞需要能归属到一个可识别但不侵犯隐私的身份）。
2. 可信的服务端计数与持久化（不能是本地点击状态，否则等于伪造互动）。
3. 限流与反滥用（防止刷赞）。
4. 撤回能力（用户可取消点赞）。
5. 审核/举报联动（与内容下架机制一致）。

在以上具备之前，实现者不应该让这个图标可点击或产生任何状态变化；如果暂不需要这个视觉位，也可以直接不实现，本设计不因此受影响。

## 8. 隐私与内容安全边界

- 三个页面中出现的所有人名、地点、心愿内容、感谢语、完成时间均为**虚构示意文案**，用于演示排版和信息层级，不对应任何真实用户、真实订单或真实对话。
- 地点全部止步于城市级别（"上海""成都""杭州"），不含道路、地标、门牌等精确位置信息。
- 时间全部为相对时间（"N 天/周前"），不出现具体日期。
- 不出现任何响应者姓名、头像、联系方式；感谢语署名统一写"心愿发布者"这一角色占位，不是具体人名。
- 不出现任何能力 URL、token、管理员/运营入口、账号登录态。
- 空态、详情页文案都明确提到"联系方式不公开""随时可申请下架"，把隐私边界写进用户可见文案，不只是内部约定。

## 9. 无障碍

- 顶栏铃铛、返回按钮、点赞按钮视觉尺寸均为 34pt，SwiftUI 落地需要用 `.contentShape(Rectangle())` 或等效方式把可点击区域扩大到 44×44pt，不能只依赖视觉大小。
- 故事卡建议整卡作为一个 `accessibilityElement(children: .combine)`，播报顺序为"交付方式 Chip → 地点时间 → 心愿正文 → 如何完成 → 感谢语"，点赞图标作为卡片内独立的次要元素，不与主卡片合并（避免点赞的可点击语义被外层卡片的导航语义吞掉）。
- 第三张"peek"故事卡在 VoiceOver 遍历顺序中应完整可读，裁切只是视觉效果，不能把这张卡从可访问树里移除（与 CL-003 首页横向卡 peek 的既有要求一致）。
- 详情页的媒体播放徽标需要 `.accessibilityLabel("播放视频")`；返回按钮需要系统标准返回语义（若用 `NavigationStack` 自带返回按钮实现，此项自动满足，不需要自定义浮层按钮时才需要手动补充 label）。
- 空态的两个整行按钮和详情页的两个 CTA 按钮都应有清晰的 `accessibilityLabel`，与可见文字一致，不需要额外加"按钮"后缀（系统 `Button` 的 `.isButton` trait 已经提供）。
- 所有字号需要在 SwiftUI 中换成语义字体（见第 6 节），保证 Dynamic Type 下不溢出裁切；本 HTML 检查点使用像素字号仅为了在固定 393×852 画板下精确对齐,不代表最终实现允许写死字号。
