## 2026-08-04 ～ 08-06　从"备份归档"到"构建上传 App Store Connect"

### 处境

工作区在一次系统降级后只剩两个归档文件（284 MB tarball + 34 MB Git bundle），本机没有 Node.js、Xcode 未激活、无任何签名证书。App Store 路线的 iOS 客户端从未被编译过。

### 关键决策与理由

**1. 生产资源不改名（`haluowode-mvp` 保留）**

品牌统一时发现 `deploy/cloudflare/wrangler.jsonc` 的 Worker 名会被 `scripts/deploy-cloudflare.mjs:61` 用来推导 D1 库名（`${name}-db`）。改名将导致部署脚本找不到 `haluowode-mvp-db` 而中断，且生产 URL 变更会打断已上线的运营台与客户端。

→ 决定：**只改用户不可见层之外的标识**（环境变量、运营台标题、导出文件名、健康检查 service），生产资源名保持不动。改名 21 处，`npm test` 24/24 通过。

**教训**：基础设施标识与品牌名是两件事，把它们耦合在一起会让改名变成数据迁移。

**2. iOS 仅支持 iPhone（`TARGETED_DEVICE_FAMILY = "1"`）**

首次上传被 Apple 以 **90474** 拒绝：工程默认通用（iPhone + iPad），但 Info.plist 只声明竖屏，iPad 多任务要求四方向齐全。

→ 决定：声明为仅 iPhone，而非补齐 iPad 四方向。理由是设计冻结稿、导航与截图从未针对 iPad，声明通用等于把未适配的界面推给 iPad 用户。

**3. deploymentTarget 16.0 → 18.0**

苹果当下的动效语言建立在 iOS 17/18 之后的 API 上（语义化弹簧、`sensoryFeedback`、`scrollTransition`、`navigationTransition(.zoom)`）。停在 16 只能手搓近似，接不住手势中断与边缘回弹。

→ 决定：抬到 18.0。本 App 无存量用户，代价接近于零；换来的是卡片原地展开这类高辨识度转场。

**4. 登录改为两段式**

原实现一进「我的」就直接呈现黑色 Sign in with Apple 按钮，突兀且浪费品牌位置。Apple 规范允许先放自有入口再呈现官方按钮，禁止的是改造按钮本身。

→ 决定：品牌入口在前，官方按钮收进弹层；三个入口共用同一个 `SignInSheet`。官方按钮未作任何样式修改。

**5. 彻底移除「感谢金」**

原设计保留一个金额申报字段，同时向 Apple 声明"App 内无支付"。这是审核最容易起疑的模糊地带。

→ 决定：App 端删除全部金额概念（选择卡、摘要行、列表与详情展示、FAQ 与隐私说明措辞），提交时 `rewardFen` 固定传 0。**服务端与生产数据库零改动**，避免为一次文案决策做数据迁移。

**6. 把运营从交付链路中移除**（进行中）

原流程：帮助者只能在 App 内"报名"，之后的匹配、沟通、上传交付全部由运营手工完成。这意味着运营是唯一同时持有双方微信/手机号的一方——**中介本身成了最大的隐私暴露面**。

→ 决定：需求方与帮助者在应用内直接完成。响应即开启站内私聊（纯文字，多会话并行）→ 需求方选定 → 帮助者提交一段文字 + 最多 9 个图片/视频 → 需求方确认完成 → 由需求方单独决定是否公开到首页故事流。运营只保留公开内容的初审。

配套：因引入陌生人即时通讯，按 App Store 指南 1.2 增加举报与拉黑（`abuse_reports`、`user_blocks`）。

## 2026-08-06　把运营从闭环中移除，并补齐四类内容审核

### 处境

上一轮把构建传上了 App Store Connect，但产品负责人在检视时发现：响应端在
App 内只做了「报名」，之后的匹配、沟通、上传交付全部由运营手工完成。这意味着
**运营是唯一同时持有双方微信/手机号的一方——中介本身成了最大的隐私暴露面**。

### 决策与理由

**1. 需求方与帮助者直接闭环，运营只保留公开内容初审**

响应即开启站内私聊（纯文字，多会话并行）→ 需求方选定 → 帮助者提交一段文字与
最多 9 个图片/视频 → 需求方确认完成 → 由需求方单独决定是否公开到首页。
服务端刻意不向发布者返回响应者联系方式，并以测试断言固定这一点。

**2. 彻底不再收集联系方式**

站内既然能沟通和交付，索取微信/手机号就只剩「平台在极端情况下能找到人」这个
很弱的理由，而它正是此前担心被审核质疑的一项。校验层不再要求，仓储层用
`account:<userId>` 占位——contact 列有 NOT NULL、responder_contact 有唯一约束，
占位既满足约束又不落任何真实联系方式，**且不需要改 schema、不需要迁移**。

**3. 信息架构调整**

搜索不再独占一栏（收进首页右上角），私聊上升为一级页面。私聊既然成了主链路，
就该有一级入口。

**4. 四类内容审核补齐**

核查发现三处缺口，其中两处直接对应 App Store 指南 1.2：
- **故事公开绕过审核**：心愿正文审过，但帮助者上传的影像从未被审过，
  需求方一点「公开」就直接上首页。改为「点公开 = 提交申请」，运营逐张查看后放行。
- **举报只进不出**：`abuse_reports` 只有一处 INSERT，没有任何查询或处理接口。
  指南要求的不只是提供举报入口，还包括对举报作出响应。补了待办、处理、
  以及「读取被举报会话」——且必须由一条具体举报触发，运营不能凭空翻阅私聊。
- **资料审核有接口没界面**：等于没人能真的去审。

| --- | --- |
| 后端测试 | 30/30（含直连交付、会话权限边界、未读、资料审核、举报处理） |
| iOS 测试 | 29/29 |
| 生产迁移 | 0007–0010 全部应用，原有数据完好 |
| 运营台 | 新增三个审核面板并发布 |
| TestFlight | 1.0.0 (3) 已上传，内部测试组就绪 |

### 路上修掉的真 bug

- `AccountResponseDTO.statusLabel` 写的是 `submitted`/`accepted`，服务端实际返回
  `pending`/`selected`——**两边从来没对上过**，响应状态从上线起就一直显示"处理中"。
- 未读数偶发漏计。根因是毫秒精度不足：同一毫秒写入的两条消息时间戳相同，
  既让显示顺序未定义，也让已读游标无法区分。改为写入时取
  `max(now, 本会话最后一条 + 1)` 保证严格递增。
- 隐私清单仍声明收集 `OtherUserContactInfo`，与实际行为矛盾；安全中心没有任何
  举报说明；三处文案还在说「平台人员协调派单」。这类「声明与实现不一致」正是
  审核员会追问、进而拖长周期的地方。

### 两个方法论教训

**测试跑的是构建产物，不是源码。** 排查未读偶发时连跑十几次 `node --test`，
一直看到"还在偶发"，几次推断都被事实推翻——真实原因是 tests 加载
`dist/server/index.js`，而我为了快绕过了会先 build 的 `npm test`。

**权限被拒不等于东西不存在。** 找 `.p8` 时搜不到就推断"下载失败""可能丢了"，
实际是 iCloud Drive 属于 macOS 受保护位置，`ls` 只回一句
`Operation not permitted`。碰到这类目录必须先验证读权限再下结论。

- `APPLE_TEAM_ID` / `APPLE_KEY_ID` / `APPLE_PRIVATE_KEY` 尚未配置，注销时的
  Apple 令牌撤销必定失败。正式审核会实测这一步，提交前必须配齐
- Beta App Review 尚未提交

## 2026-08-03　从微信小程序回到 App Store

### 处境

小程序 0.1 已是可提审状态，但真实上线仍卡在微信主体资质（开放平台"移动应用"不接受个人主体）。产品负责人重新评估后决定投入 Apple Developer Program。

### 决策

新开 `appstore/1.0` 分支，以冻结的 1.0 玫粉白客户端为基线，补齐 App Store 的准入项：Sign in with Apple（客户端 + 服务端验签 + 令牌撤销）、App 内账户删除、相册仅添加权限、隐私清单（PrivacyInfo）、隐私政策与服务条款、提审清单。

`fd37505` 将发布与响应改为**必须登录**——这条决定后来产生了连锁影响：主链路的端到端验证从此依赖 Apple 会员，"开发能做完，但验证做不完"。

## 2026-07-19 ～ 07-20　微信小程序 0.1 转向与回退

### 处境

iOS 1.0 已冻结并真机验证，但分发需要 Apple Developer Program 年费。产品负责人判断这不适合作为早期验证成本。

### 决策

近期目标从 TestFlight 改为**微信小程序 0.1 真实试用**。关键约束：复用已上线的 Cloudflare Worker + D1 + R2，账号层改为 **provider-neutral**（先接微信，未来接 Apple），不因换客户端重做业务数据。

`WX-001` 交付原生小程序工程、Worker/D1 的账户与会话、本人发布/响应、发布者确认完成、账户删除匿名化。`WX-002` 修复了嵌套 worktree 的构建产物污染根目录 lint 的问题（实际输出 5 error / 1804 warning，全部来自其他 worktree 的 `dist/`）。

### 回过头看

provider-neutral 这个决定是这一阶段最有价值的产物。8 月回到 App Store 时，账号层几乎原样可用，只需增加一个 Apple provider——没有因为平台转向而重做数据模型。

## 2026-07-19　1.0 视觉基线冻结

### 处境

存在两条并行的视觉方向：工程实现的 v3 暖蓝，与 Claude 交付的玫粉白/Lucide 版本。多个 worktree 同时演进，主线难以判断哪一版是"产品"。

### 决策

产品负责人认可玫粉白版本，将 `463a420`（设计主提交 `8e95b0b`）**冻结为唯一的 1.0**，固定为 `release/1.0` 分支与 `v1.0-claude-rose` 标签，并清理全部历史并行 worktree。此后"1.0 版本"一词只指这一个精确提交。

同期确立的产品边界（至今有效）：首页不是第二个市场；MVP 没有关注、私信、评论或伪造点赞数；Dock 不显示汉字但保留 VoiceOver 名称与 44pt 命中区；公开故事需发布者单独同意。

### 回过头看

"用一个 commit hash 定义产品版本"解决了多线并行时的指代混乱。代价是此后所有改动都必须显式说明是否动了冻结基线。

## 2026-07-15 ～ 07-18　MVP 后端上线与 iOS 客户端从零构建

### 处境

产品从网页原型起步。需要在没有专职团队的情况下，同时推进后端、iOS 客户端与设计。

### 决策

采用**多 AI 分工 + 强制验收**的协作制度（见 `AGENTS.md`）：Codex 负责拆解、架构、安全边界、独立验收与集成；Antigravity 负责工程实现；Claude 负责设计判断。核心规则是"完成 ≠ 可继续"——交付方必须停止，只有协调人独立复验后才能进入下一任务。

技术上确立了至今未变的架构：Cloudflare Worker + D1 + R2，交付文件以随机能力令牌访问，运营台 PIN 保护，人工审核前置。

### 回过头看

这套制度产生了大量文档开销，但也换来了可追溯性：每个决定都能回溯到具体的验收证据。本次 8 月的工作能在归档重建后快速恢复，直接得益于此。
