## 2026-08-06　Apple 令牌撤销闭环，构建 7 上传

### 处境

Apple 令牌撤销是提审路上最后一个卡口：Apple 要求支持账户删除的 App 必须在删除时撤销登录令牌，审核会实测。代码路径早就写好，但线上一直缺 `APPLE_TEAM_ID`、`APPLE_KEY_ID`、`APPLE_PRIVATE_KEY` 三个密钥，等于必定失败。

### 决策与理由

**1. 先用真实端点验密钥，再写生产配置**

拿到 `.p8` 之后没有直接写进生产，而是先用与 `server/apple-identity.ts` 完全相同的方式构造 client_secret，携一个必定无效的 code 打 Apple 的 `/auth/token`。看的是它**怎么拒绝**：`invalid_client` 说明凭据不对，`invalid_grant` 说明凭据没问题、只是 code 假。实际返回 `invalid_grant`，于是 Team ID、Key ID、私钥、bundle 四项匹配这件事在写任何配置之前就已确定。这次探测不写任何东西，失败也没有代价。

**2. 认定「数据库状态」不能作为撤销成功的证据**

删除账户后数据库会呈现一组很像成功的状态：token 清空、subject 抹除、会话全撤。但 `worker/index.ts:326` 明确写着撤销失败不回滚删除——所以这组状态在「撤销成功」和「撤销失败但账户照删」两种情况下完全一样。最终以 Apple ID 设置里「使用您 Apple ID 的 App」列表中 Gratia 消失作为唯一证据。

**3. 记下一个会让验收误判的陷阱**

`refresh_token` 只在**登录那一刻**用 `authorizationCode` 换取。密钥配置之前登录的账户，这一列是 NULL；而删除时只查非空的 identity，`appleTokensRevoked` 又初始化为 `true`——于是删这类旧账户会返回 `true`，却一次 Apple 调用都没发生。当时生产库里唯一那个账户正是这个状态，直接拿它验收必然误判。正确顺序是先重新登录、确认 `refresh_token` 非空，再删。

### 结果

四步全部走通：凭据探测 `invalid_grant` → 重新登录后 `refresh_token` 由 NULL 变非空 → 删除后 token 清空、2 条会话全撤 → Apple ID 设置里 Gratia 消失。**第二步本身就证明了生产 Worker 用这三个真实密钥成功调用了 Apple 真实端点**：要存下这个值，读密钥、解析 PEM、签 ES256、Apple 返 200 四件事必须全成，任何一环失败都只会存 NULL。

构建 7 已上传并 VALID，是第一个包含地点搜索改动的构建。

### 未验证项

- 撤销只在**一个账户**上验证过一次。Apple 审核用的是全新账户，路径相同但未重复验证。
- 本次未做真机长期安装验证，构建 7 只经 TestFlight 处理为 VALID。

## 2026-08-06　iOS 签名：两个会安静报「成功」的坑

### 处境

打构建 7 时才发现，仓库里没有留下可复用的签名流程——交接文档指向的 `scratchpad/signing` 早已不存在。

### 决策与理由

第一次归档失败，报的是「Your team has no devices from which to generate a provisioning profile」。**这个错误具有误导性**：真正的问题不是没有设备，而是 XcodeGen 默认写死 `CODE_SIGN_IDENTITY = "iPhone Developer"`，把自动签名锁在 development 上，于是它去要一个 App Store 构建根本不需要的 development 描述文件；个人团队没有注册设备，Apple 就拒绝签发。

顺着错误提示走会掉进第二个坑：把 `CODE_SIGN_IDENTITY` 设成空值确实让 `ARCHIVE SUCCEEDED` 了，**但产物完全没有签名**——没有 `embedded.mobileprovision`、没有任何 entitlements。这意味着 `com.apple.developer.applesignin` 不在产物里，**Sign in with Apple 直接失效**，而登录与账户删除整条链都建立在它上面。`xcodebuild` 全程不报一个字，不打开产物看是发现不了的。

→ 决定：签名参数固定写进 `ios/project.yml` 的 **Release** 配置（Manual + `Apple Distribution` + `Gratia App Store`），命令行不再覆盖——正是「命令行传了一个把签名关掉的值」造成了第二个坑。同时把流程固化为 `scripts/ios-release.mjs`，并在归档后**强制校验产物**：签名主体、Team ID、`applesignin` entitlement、构建号一致，缺一项就中断。

构建号核对也放进同一个脚本。构建号一经上传即被占用且不可复用，而本地 `project.yml` 并不知道线上到了几，撞号要等到上传那一刻才报错。

### 结果

构建 7 归档、导出、验证、上传全部通过，产物确认为 Apple Distribution 签名且带 `applesignin`。脚本的撞号检查已用构建 7 实测：置 `CURRENT_PROJECT_VERSION: 7` 时正确中断并提示改用 8。Debug 配置未受影响，iOS 测试仍 41/41。

### 未验证项

- 脚本只在这一次完整链路上跑通过。证书或描述文件过期后的表现（都在 2027-08 到期）未验证。
- `scripts/ios-release.mjs` 假定描述文件名为 `Gratia App Store` 且已存在于本机；ASC 上重建描述文件的路径没有写进脚本。

## 2026-08-06　发布页地点：从五个写死的城市改为 MapKit 补全

### 处境

发布流程第一步要求从「杭州、上海、北京、深圳、广州」五个胶囊里选一个城市，`city` 的默认值直接写死为「杭州」。这与产品本身的主张冲突——**替远方的人去现场**，而「远方」不该由客户端的一个数组定义。上一位接手者已写好改动，但测试没跑完就中断了，工作区留下 5 个未提交、状态未知的文件。

### 决策与理由

**1. 用 `MKLocalSearchCompleter`，不引入第三方地点服务**

它不需要 API Key、不产生费用、全球覆盖，最关键的是**只做文本检索、不读取设备位置**，因此不必申请定位权限——与现有的「不收集联系方式、不申请定位」声明一致。引入 Google Places 之类会同时增加成本、隐私声明与审核解释成本。

**2. 允许手输，不强制从建议里选**

有些地方（老家巷口的那棵树）本来就不在任何地图数据库里。强制选择等于把这类心愿排除在外，而它们恰恰是这个产品最想承接的。

**3. 拆分逻辑必须保证「永远可提交」**

服务端要求 `city` 与 `landmark` 分开，各有 2–24 / 2–40 字的校验，而补全结果只给「名称 + 地区」。界面上**只有一个地点输入框，没有城市输入框**——这意味着城市一旦拆错，用户在界面上无从修复。因此拆分的正确性目标不是「拆得漂亮」，而是**结果必须落在服务端的校验窗口内**：拆不出合用的城市时退回地点名，超长则截断，绝不留空或原样带过去。

接手复验时发现原改动在这一点上有三处会真实卡住用户的缺陷，均已修复：

- 手输时把地标原样镜像进城市。地标上限 40 而城市上限 24，于是 25–40 字的地点必定卡在「城市名称必须为2-24个字符」上，且错误提示指向一个界面上不存在的字段。
- 中文地区串通常**不带分隔符**（「中国浙江省杭州市西湖区」），按逗号切分取第一段会得到整串。改为切掉国名与省级前缀后取到地级后缀为止，并处理「丽江市玉龙纳西族自治县」（不能被后面的「自治县」抢走）与「西双版纳傣族自治州景洪市」（地级州套县级市）两类。
- 提交失败后返回这一步重填时，草稿回填被当作手输处理，会把已拆好的「杭州」悄悄覆盖成「西湖断桥」。

### 结果

iOS 41/41 通过（原 29 + 新增 12 条地点拆分用例），后端 30/30，`npm run lint` 零输出，构建无告警。新增的 12 条用例覆盖省市区、直辖市、自治区、自治州套市、逗号分隔、特别行政区、拉丁地址、前置邮编与空 subtitle，并逐条断言结果落在 2–24 字窗口内。

构建号从 6 改为 7：经 App Store Connect API 核实，构建 1–6 均已上传，且**构建 6 比这批改动早约一小时上传，不含本次内容**。原改动把版本停在已被占用的 6 上，照此打包上传必被拒。

### 未验证项

- **补全结果的真实形态未在真机/模拟器上人工核对过。** 拆分逻辑是按 Apple 中文地址的惯例格式写的并有单元测试，但 `MKLocalSearchCompleter` 实际返回的 `subtitle` 格式没有逐一验证，境外地点尤其如此。
- 拉丁字母地址一律取第一段（去掉前置邮编）。对「Paris, France」「Mountain View, CA, United States」正确，对「Champ de Mars, 5 Av. Anatole France, 75007 Paris, France」这类多段地址会取到「Champ de Mars」而不是「Paris」——是一个人能看懂的地点，但不是城市。各国地址格式差异太大，猜错比取第一段更糟，故不再往下猜。
- 本次未上传新构建，TestFlight 上仍是不含此改动的构建 6。

## 2026-08-04 ～ 08-06　从"备份归档"到"构建上传 App Store Connect"

### 处境

工作区在一次系统降级后只剩两个归档文件（284 MB tarball + 34 MB Git bundle），本机没有 Node.js、Xcode 未激活、无任何签名证书。App Store 路线的 iOS 客户端从未被编译过。

### 关键决策与理由

**1. 生产资源不改名（`haluowode-mvp` 保留）**

品牌统一时发现 `deploy/cloudflare/wrangler.jsonc` 的 Worker 名会被 `scripts/deploy-cloudflare.mjs:61` 用来推导 D1 库名（`${name}-db`）。改名将导致部署脚本找不到 `haluowode-mvp-db` 而中断，且生产 URL 变更会打断已上线的运营台与客户端。

→ 决定：**只改用户不可见层之外的标识**（环境变量、运营台标题、导出文件名、健康检查 service），生产资源名保持不动。改名 21 处，`npm test` 24/24 通过。

**教训**：基础设施标识与品牌名是两件事，把它们耦合在一起会让改名变成数据迁移。

**2. iOS 仅支持 iPhone（`TARGETED_DEVICE_FAMILY = "1"`）**

首次上传被 Apple 以 **90474** 拒绝：工程默认通用（iPhone + iPad），但 Info.plist 只声明竖屏，iPad 多任务要求四方向齐全。

→ 决定：声明为仅 iPhone，而非补齐 iPad 四方向。理由是设计冻结稿、导航与截图从未针对 iPad，声明通用等于把未适配的界面推给 iPad 用户。

**3. deploymentTarget 16.0 → 18.0**

苹果当下的动效语言建立在 iOS 17/18 之后的 API 上（语义化弹簧、`sensoryFeedback`、`scrollTransition`、`navigationTransition(.zoom)`）。停在 16 只能手搓近似，接不住手势中断与边缘回弹。

→ 决定：抬到 18.0。本 App 无存量用户，代价接近于零；换来的是卡片原地展开这类高辨识度转场。

**4. 登录改为两段式**

原实现一进「我的」就直接呈现黑色 Sign in with Apple 按钮，突兀且浪费品牌位置。Apple 规范允许先放自有入口再呈现官方按钮，禁止的是改造按钮本身。

→ 决定：品牌入口在前，官方按钮收进弹层；三个入口共用同一个 `SignInSheet`。官方按钮未作任何样式修改。

**5. 彻底移除「感谢金」**

原设计保留一个金额申报字段，同时向 Apple 声明"App 内无支付"。这是审核最容易起疑的模糊地带。

→ 决定：App 端删除全部金额概念（选择卡、摘要行、列表与详情展示、FAQ 与隐私说明措辞），提交时 `rewardFen` 固定传 0。**服务端与生产数据库零改动**，避免为一次文案决策做数据迁移。

**6. 把运营从交付链路中移除**（进行中）

原流程：帮助者只能在 App 内"报名"，之后的匹配、沟通、上传交付全部由运营手工完成。这意味着运营是唯一同时持有双方微信/手机号的一方——**中介本身成了最大的隐私暴露面**。

→ 决定：需求方与帮助者在应用内直接完成。响应即开启站内私聊（纯文字，多会话并行）→ 需求方选定 → 帮助者提交一段文字 + 最多 9 个图片/视频 → 需求方确认完成 → 由需求方单独决定是否公开到首页故事流。运营只保留公开内容的初审。

配套：因引入陌生人即时通讯，按 App Store 指南 1.2 增加举报与拉黑（`abuse_reports`、`user_blocks`）。

## 2026-08-06　把运营从闭环中移除，并补齐四类内容审核

### 处境

上一轮把构建传上了 App Store Connect，但产品负责人在检视时发现：响应端在
App 内只做了「报名」，之后的匹配、沟通、上传交付全部由运营手工完成。这意味着
**运营是唯一同时持有双方微信/手机号的一方——中介本身成了最大的隐私暴露面**。

### 决策与理由

**1. 需求方与帮助者直接闭环，运营只保留公开内容初审**

响应即开启站内私聊（纯文字，多会话并行）→ 需求方选定 → 帮助者提交一段文字与
最多 9 个图片/视频 → 需求方确认完成 → 由需求方单独决定是否公开到首页。
服务端刻意不向发布者返回响应者联系方式，并以测试断言固定这一点。

**2. 彻底不再收集联系方式**

站内既然能沟通和交付，索取微信/手机号就只剩「平台在极端情况下能找到人」这个
很弱的理由，而它正是此前担心被审核质疑的一项。校验层不再要求，仓储层用
`account:<userId>` 占位——contact 列有 NOT NULL、responder_contact 有唯一约束，
占位既满足约束又不落任何真实联系方式，**且不需要改 schema、不需要迁移**。

**3. 信息架构调整**

搜索不再独占一栏（收进首页右上角），私聊上升为一级页面。私聊既然成了主链路，
就该有一级入口。

**4. 四类内容审核补齐**

核查发现三处缺口，其中两处直接对应 App Store 指南 1.2：
- **故事公开绕过审核**：心愿正文审过，但帮助者上传的影像从未被审过，
  需求方一点「公开」就直接上首页。改为「点公开 = 提交申请」，运营逐张查看后放行。
- **举报只进不出**：`abuse_reports` 只有一处 INSERT，没有任何查询或处理接口。
  指南要求的不只是提供举报入口，还包括对举报作出响应。补了待办、处理、
  以及「读取被举报会话」——且必须由一条具体举报触发，运营不能凭空翻阅私聊。
- **资料审核有接口没界面**：等于没人能真的去审。

### 结果

| 项目 | 结果 |
| --- | --- |
| 后端测试 | 30/30（含直连交付、会话权限边界、未读、资料审核、举报处理） |
| iOS 测试 | 29/29 |
| 生产迁移 | 0007–0010 全部应用，原有数据完好 |
| 运营台 | 新增三个审核面板并发布 |
| TestFlight | 1.0.0 (3) 已上传，内部测试组就绪 |

### 路上修掉的真 bug

- `AccountResponseDTO.statusLabel` 写的是 `submitted`/`accepted`，服务端实际返回
  `pending`/`selected`——**两边从来没对上过**，响应状态从上线起就一直显示"处理中"。
- 未读数偶发漏计。根因是毫秒精度不足：同一毫秒写入的两条消息时间戳相同，
  既让显示顺序未定义，也让已读游标无法区分。改为写入时取
  `max(now, 本会话最后一条 + 1)` 保证严格递增。
- 隐私清单仍声明收集 `OtherUserContactInfo`，与实际行为矛盾；安全中心没有任何
  举报说明；三处文案还在说「平台人员协调派单」。这类「声明与实现不一致」正是
  审核员会追问、进而拖长周期的地方。

### 两个方法论教训

**测试跑的是构建产物，不是源码。** 排查未读偶发时连跑十几次 `node --test`，
一直看到"还在偶发"，几次推断都被事实推翻——真实原因是 tests 加载
`dist/server/index.js`，而我为了快绕过了会先 build 的 `npm test`。

**权限被拒不等于东西不存在。** 找 `.p8` 时搜不到就推断"下载失败""可能丢了"，
实际是 iCloud Drive 属于 macOS 受保护位置，`ls` 只回一句
`Operation not permitted`。碰到这类目录必须先验证读权限再下结论。

### 未验证

- 触感反馈与转场手感需真机实测
- `APPLE_TEAM_ID` / `APPLE_KEY_ID` / `APPLE_PRIVATE_KEY` 尚未配置，注销时的
  Apple 令牌撤销必定失败。正式审核会实测这一步，提交前必须配齐
- Beta App Review 尚未提交

## 2026-08-03　从微信小程序回到 App Store

### 处境

小程序 0.1 已是可提审状态，但真实上线仍卡在微信主体资质（开放平台"移动应用"不接受个人主体）。产品负责人重新评估后决定投入 Apple Developer Program。

### 决策

新开 `appstore/1.0` 分支，以冻结的 1.0 玫粉白客户端为基线，补齐 App Store 的准入项：Sign in with Apple（客户端 + 服务端验签 + 令牌撤销）、App 内账户删除、相册仅添加权限、隐私清单（PrivacyInfo）、隐私政策与服务条款、提审清单。

`fd37505` 将发布与响应改为**必须登录**——这条决定后来产生了连锁影响：主链路的端到端验证从此依赖 Apple 会员，"开发能做完，但验证做不完"。

## 2026-07-19 ～ 07-20　微信小程序 0.1 转向与回退

### 处境

iOS 1.0 已冻结并真机验证，但分发需要 Apple Developer Program 年费。产品负责人判断这不适合作为早期验证成本。

### 决策

近期目标从 TestFlight 改为**微信小程序 0.1 真实试用**。关键约束：复用已上线的 Cloudflare Worker + D1 + R2，账号层改为 **provider-neutral**（先接微信，未来接 Apple），不因换客户端重做业务数据。

`WX-001` 交付原生小程序工程、Worker/D1 的账户与会话、本人发布/响应、发布者确认完成、账户删除匿名化。`WX-002` 修复了嵌套 worktree 的构建产物污染根目录 lint 的问题（实际输出 5 error / 1804 warning，全部来自其他 worktree 的 `dist/`）。

### 回过头看

provider-neutral 这个决定是这一阶段最有价值的产物。8 月回到 App Store 时，账号层几乎原样可用，只需增加一个 Apple provider——没有因为平台转向而重做数据模型。

## 2026-07-15 ～ 07-18　MVP 后端上线与 iOS 客户端从零构建

### 处境

产品从网页原型起步。需要在没有专职团队的情况下，同时推进后端、iOS 客户端与设计。

### 决策

采用**多 AI 分工 + 强制验收**的协作制度（见 `AGENTS.md`）：Codex 负责拆解、架构、安全边界、独立验收与集成；Antigravity 负责工程实现；Claude 负责设计判断。核心规则是"完成 ≠ 可继续"——交付方必须停止，只有协调人独立复验后才能进入下一任务。

技术上确立了至今未变的架构：Cloudflare Worker + D1 + R2，交付文件以随机能力令牌访问，运营台 PIN 保护，人工审核前置。

### 回过头看

这套制度产生了大量文档开销，但也换来了可追溯性：每个决定都能回溯到具体的验收证据。本次 8 月的工作能在归档重建后快速恢复，直接得益于此。

## 记录规范

**任何人接手本项目，完成一个有意义的迭代后都必须在此追加记录。** 判定标准：改变了产品形态、技术选型、平台策略或对外承诺的改动，都算。

每条记录写四件事：**处境 → 决策与理由 → 结果 → 未验证项**。不写流水账，不写"完成了 XX 任务"这类无信息量的句子；重点是**为什么这么选、放弃了什么**。

本文件与 `PROJECT_LOG.md` 分工不同：`PROJECT_LOG.md` 是只追加的验收证据（命令输出、测试数、commit SHA），供追溯与裁决；本文件是决策与权衡的叙述，供复盘与对外讲述。两者都要写。
