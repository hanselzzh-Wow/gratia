# 实现智能体交付质量门

适用对象：Antigravity/Gemini 及后续承担实现任务的智能体。目的不是限制任务复杂度，而是确保复杂交付可以被独立复现和验收。

## 1. 先证明事实，再写结论

- “通过”“已接入”“已移除”“可运行”都必须附可复现证据，不能只写自然语言结论。
- 命令退出码为 0 不等于功能通过；必须核对实际发现的测试数量、断言数量、构建目标和运行平台。
- parser、lint、静态扫描、单元测试、模拟器构建、真机运行属于不同证据，禁止互相冒充。
- 当前环境无法验证的事项必须明确列为“未验证”，不得用条件编译、dummy 或空实现把失败变成绿色。

## 2. 交付前四次自检

1. **成果存在性**：任务要求的页面、类型、入口和测试文件都存在且非空。
2. **行为真实性**：没有用 Mock、假延时、空 fallback 或吞错替代任务要求的真实行为。
3. **验证有效性**：测试清单非空，失败路径确实会让命令失败；构建命令覆盖被修改的目标。
4. **声明一致性**：逐项将交接中的每个完成声明与代码、命令原始输出对应；无法对应的声明删除或降级为未验证。

## 3. 必交证据

- 精确 commit SHA 和 `git show --stat` 摘要。
- 修改文件清单，以及任务要求但未修改文件的解释。
- 每条验收命令、退出码和关键原始输出；测试必须包含发现数、执行数、通过数。
- 静态扫描的完整查询范围与命中解释，不能只扫描最容易通过的子目录。
- 已验证/未验证/已知风险三栏；不得把未来环境可能通过写成当前已通过。
- 交付前的 `git status --short`，证明没有遗漏未跟踪成果。

## 4. 禁止的假绿模式

- 用 `#if canImport(...)` 把全部测试排除，并保留一个空 fallback。
- 删除或清空页面来消除 Mock/警告扫描命中。
- 只运行语法 parser，却声称 App 已编译。
- 测试文件存在，但测试发现列表为空。
- 只验证成功响应，不验证请求 method、path、query、body、错误和取消。
- 交接报告描述了未出现在 commit 或工作区中的文件。

## 5. Codex 独立验收

- Codex 不接受智能体自报结果作为最终证据，会在干净状态重新运行命令并检查覆盖范围。
- 任一 P0 事实与交接矛盾，任务退回原分支追加修订，不重写历史，以保留能力评估轨迹。
- 连续两次出现同类假绿时，下一任务缩小写入范围并增加中途检查点；连续两次独立验收通过后再扩大任务复杂度。
- 主分支合入、生产部署、签名和最终安全裁决始终由 Codex/用户完成。
